## Blind take (written before opening design.md / tasks.md / the delta)

Sources: proposal Why, `openspec/specs/embeddable-kernel/spec.md`, bead `conduit-embed-pdu`, Matrix room v11 (redaction list fetched from spec.matrix.org), and the code in `event.rs`, `hashing.rs`, `signing.rs`, `redaction.rs`, `storage_pg.rs`, `federation/{server,client,pipeline,queue}.rs`, `event_pipeline.rs`.

1. **Pin: the ID is derived on every inbound path, never read.** Today `/send` keys results and dedup on the wire `event_id` (`server.rs:178,190`, `pipeline.rs:96-100`). A v11 PDU from Synapse has no `event_id`, so it fails to parse at all.
2. **Pin: fetch-by-ID must compare the derived ID with the ID you asked for.** `fetch_missing_auth_events` (`pipeline.rs:330-345`) stores whatever `/event/{id}` returns, unverified, under the wire `event_id`. That is DAG poisoning today. Once the ID is derived, the check `derived == requested` is the whole defence.
3. **Pin: co-signing is not signing.** `/invite` calls `sign_event` on a foreign PDU (`server.rs:483`). That rewrites `hashes` from our own re-serialisation. Any field we drop, or any byte we normalise, changes the hash and therefore the event ID. Co-sign needs an add-signature-only operation. `/invite` also never verifies the inviter's signature before we co-sign and store it.
4. **Pin: the v11 redaction keep-list includes `event_id`.** The spec's top-level list is `event_id, type, room_id, sender, state_key, content, hashes, signatures, depth, prev_events, auth_events, origin_server_ts`. Synapse's `prune_event_dict` keeps `event_id` too. A wire `event_id` key is therefore protocol data that redaction keeps and both hashes cover. It is not local metadata.
5. **Pin: outbound wire never carries the local ID.** `send_transaction`, the queue payload (`queue.rs:104,293`), `/state`, `/backfill`, `/event`, `/get_missing_events`, the `/send_join` echo and the `/invite` response all serialise `Event`. Synapse hashes an extra `event_id` key, so it derives a different ID and its signature check fails.
6. **Pin: one row decoder.** `storage_pg.rs` rebuilds `Event` by hand in about ten places (214, 280, 812, 849, 887, 952, 988, 1079, 1126, 1194). Adding extensions means ten chances to drop one silently.
7. **Refuse: trusting legacy rows.** Before `56498e3`, local events were hashed with `"event_id": ""` included. Pre-change remote rows also lost their unknown fields at ingest. Neither kind of row can reproduce its own ID. The migration must detect them, not assume they are fine.
8. **Pin: the PG boundary.** JSONB cannot store `\u0000`, and it normalises numbers. Either keep the PDU as text, or name what gets rejected.
9. **Pin: make_join template and path IDs.** Drop `"event_id": "$placeholder"` (`server.rs:322`). The `send_join` and `invite` handlers ignore the `:eventId` path segment.
10. **Tradeoff I would accept:** a flattened JSONB extension map next to the existing columns, rather than a raw-PDU column, provided items 6 and 7 hold.

## Comparison against design.md, tasks.md, and the delta

The design matches most of the take: a `Pdu`/`Event` split, crypto that accepts only `Pdu`, the ID derived on `/send`, `/send_join`, `/invite` and auth fetches, path IDs checked against derived IDs, a `make_join` template without `event_id`, legacy outbox envelopes converted to `Pdu`, a JSONB extension map with an empty default, every projection updated, and the live Synapse check. Those are the right bones, and pins 1, 5 and 9 are answered.

The design gets one cryptographic boundary wrong, and it is silent on four items that matter for interop or security.

## Required amendments (send-back)

1. **Wire `event_id` is a v11 key that redaction keeps, so do not reject it as local metadata.** The design says "Wire deserialization rejects `event_id`" and "rejects extension keys that collide with ... local metadata". The delta says reference hashing uses "no ... local metadata". Under v11 a received PDU carrying a top-level `event_id` key is still well formed. Synapse accepts it, keeps it through pruning, and includes it in the content hash, the reference hash and the signed bytes. If Conduit rejects such an event, any server in the room can partition Conduit from it: Conduit rejects the event, then everything that names it in `prev_events` or `auth_events`.
   Required wording in the delta:
   - The derived ID lives only on `Event`.
   - A wire `event_id` key is opaque protocol data, held in `Pdu` (for example `wire_event_id: Option<Value>`, or kept in the extension map), retained by v11 redaction, and covered by both hashes and by signatures.
   - The wire key is never read as identity, and it is never compared with the derived ID.
   - Conduit-authored PDUs never set it.
   - The flattened local snapshot layout cannot tell this key from the local ID. New persisted envelopes must therefore nest (`{"event_id": ..., "pdu": {...}}`) or store the `Pdu` alone; the flattened layout stays read-only for legacy rows.
   - Add a vector: a PDU that carries an `event_id` key, with Synapse-computed content hash and reference hash.
2. **Split authoring from co-signing.** Add `add_signature(&mut Pdu, key, server)`, which signs the v11-redacted bytes and leaves `hashes` untouched. `/invite` (and later the restricted-join resident signature) uses it. `/invite` must run `verify_event_and_hash` on the inviter's PDU, and derive and compare the path ID, before it co-signs or persists. Scenario: after a co-sign, `hashes` and the derived ID are byte-identical to the inviter's.
3. **Every fetch-by-ID verifies the derived ID.** This covers `client.event()`, the auth-event fetch in `pipeline.rs:330-345`, and any `get_missing_events`, `backfill` or `state` result that is later stored. The rule: decode as `Pdu`, derive the ID, require `derived == requested` (or that the derived ID is in the referenced set), and verify signatures before `put_event`. Scenario: a peer that answers `/event/$A` with a different valid event is refused, and nothing is stored.
4. **Migration ID-integrity check.** As part of the migration, or a one-shot check at startup, recompute the reference hash of every existing `events` row and compare it with the `event_id` primary key. Rows that mismatch are the pre-`56498e3` local events and the lossy remote ones. Report them, never serve them over federation, and do not rewrite their primary key. Add the column as `NOT NULL DEFAULT '{}'::jsonb`; that default is metadata-only on PG 11 and later, so the table is not rewritten.
5. **One PG row decoder.** All `events` read paths go through a single row-to-`Event` function. Add a test that writes an extended PDU and reads it back through each public `Storage` read method, both PG and in-memory, and asserts the extensions survive. The design's "every projection includes extensions" needs this to be checkable.
6. **Name the JSONB limits in the delta.** Postgres JSONB rejects a `\u0000` string escape. Either store the received PDU as canonical text (the authoritative bytes, with the existing columns as projections), or state that such events fail ingest with a typed error, and test it. This is pre-existing for `content`, but the delta now promises durable wire preservation.
7. **Typed outbound boundary.** Federation emitters (`send_transaction`, the queue envelope, the `state`/`backfill`/`event`/`get_missing_events`/`send_join`/`invite` responses, and outbound `invite`/`send_join` bodies) take `&Pdu` or `Vec<Pdu>`, never `&Event`. If `Event: Deref<Target = Pdu>` stays, `json!({"pdus": events})` still compiles and still leaks, so the type has to be enforced at the function signature. Add one test that serialises each response and asserts no top-level `event_id`.

## Notes for act (non-blocking, ranked)

1. **Content-hash divergence to document.** Synapse's `compute_content_hash` also pops top-level `age_ts`, `outlier` and `destinations`; check this in `synapse/crypto/event_signing.py`. The spec strips only `hashes`, `signatures` and `unsigned`. Follow the spec, and record the divergence: Conduit redacts an adversarial PDU with one of those keys where Synapse does not. The result is redaction, not rejection, so the DAG still converges.
2. **Validate canonical JSON over the whole received object, as Synapse does** (`validate_canonicaljson` after unsigned stripping). Like Synapse's `_strip_unsigned_values`, keep only allowlisted remote `unsigned` keys (`age`, `invite_room_state`, `knock_room_state`) and do not persist the rest.
3. **`send_join` v2 `state`** is meant to be the state before the join; today it is the current state, which includes the join. `make_join` ignores repeated `ver` parameters (`Query<HashMap<String,String>>`) and never returns `M_INCOMPATIBLE_ROOM_VERSION`. `send_join` does not check `state_key == sender` or that the sender's domain matches the origin. None of these are format work. File beads for them.
4. **No `/event_auth` route exists.** It is not a format change, but Synapse calls it during auth-chain repair. File a bead if none exists.
5. **Fixture vector in CI.** Keep the live Synapse check, and also check in one Synapse-authored v11 PDU (with an extension key, without `event_id`), its expected ID, and the signing key. The invariant should not depend on Docker.
6. **The proposal's "sign then fill event_id then verify" property** is trivially true once the types are split. The tests that bite are: an extension changes the content hash but not the reference hash; a hash mismatch produces a redacted PDU whose ID and `hashes` are unchanged; and amendments 1-3.

`tasks.md` carries no boxes by design (bd tracks work), so the owed amendments are recorded on `conduit-embed-pdu` rather than added as Markdown boxes.
