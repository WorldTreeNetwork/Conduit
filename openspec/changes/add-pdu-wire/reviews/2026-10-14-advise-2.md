## A1 rebuttal: upheld

The author is right, and the first review's premise was wrong for v3+ rooms. I verified each claim independently.

- **Spec.** `rooms/v3`: "When events are sent over federation, the `event_id` field is no longer included. A server receiving an event should compute the relevant event ID for itself." The v11 PDU table has no `event_id`. The v11 redaction keep-list still names `event_id`. The v3 page puts that algorithm under "Unchanged from v2 ... included for completeness" and never reconciles the two. The keep-list entry is vestigial. It does not permit the key.
- **Synapse 1.162.0.** `event_dict_from_json_str` (`rust/src/events/mod.rs:686`) maps `ROOM_V3 | ROOM_V4_PLUS` to `EventFormatV2V3`. Room v11 uses `ROOM_V4_PLUS`, and only Hydra (`ROOM_V11_HYDRA_PLUS`) uses `EventFormatV4`.
- **Synapse validation.** `formatted_event.validate()` then runs `EventFormatV2V3::validate`, which bails with "v2/v3 events must not have an explicit event_id" (`formats/v2v3.rs:49-52`). `make_event_from_json` turns that `ValueError` into `SynapseError(400, BAD_JSON)`, and `_handle_pdus_in_txn` logs "Ignoring PDU for failing to deserialize" and `continue`s (`federation_server.py:487-491`), so the PDU gets no result entry.
- **Version.** `9e2a076144` ("Port Event class to Rust (#19701)") is contained in `v1.155.0` and `v1.162.0` and not in `v1.154.0`. The same check exists in `v2v3.rs` at both tags.

Refusing the key keeps Conduit on the same side as the pinned peer. The adopted half of A1 holds: the ID lives only on `Event`, a wire ID is never used as identity, authored PDUs carry no `event_id`, new envelopes nest, the flattened layout is read-only, and a negative fixture replaces the vector that cannot be produced. The recorded residual risk, an old Synapse or another implementation that emits the key, is stated with a trigger to revisit. That disposition is acceptable.

## Required amendments (send-back)

### B1. A6 protects `events.pdu_json`, but other Postgres sinks still reject `\u0000`, and one of them sits before the decoder.

A6 says: "Refusing at ingest would let any room member wedge Conduit with a spec-valid event." That reasoning holds, but the contract still leaves these paths open.

- **The inbound replay table runs before any PDU is parsed.** `send_transaction` (`federation/server.rs:139-146`) calls `Replay::body`, which stores the whole transaction body in `transactions.request JSONB` (migration `0011`, `storage_pg.rs:96-106`). If one spec-valid PDU in the body contains `\u0000`, that INSERT fails and `/send` returns 500 for the whole transaction, EDUs included. The origin then backs off and retries the destination. This is worse than the single-event wedge A6 set out to prevent. As written, the "Pool restart" scenario passes at the storage layer, while the same PDU delivered over `/send` never reaches storage.
- **`transactions.result JSONB`.** Per-PDU error strings are stored there. A `PduDecodeError` or a serde message that echoes a string value containing U+0000 makes `finish_transaction` fail.
- **`fed_outbound_queue.payload JSONB`** (migration `0006`). New envelopes `{"pdus":[Pdu..]}` with a NUL fail in `enqueue_outbound`. `persist_and_signal` (`queue.rs:120-133`) only logs the failure. A local state event with NUL in, say, its `topic` content is then persisted locally and never federated. The divergence is silent.
- **Typed projection columns.** These include `events.type`, `events.state_key`, `events.sender` and `events.room_id` (`TEXT`), `auth_events`/`prev_events` (`TEXT[]`), `hashes` and `signatures` (`JSONB`), and `room_current_state(room_id, type, state_key)`. PostgreSQL `TEXT` rejects 0x00 as well. U+FFFD substitution, the design's remedy for `content`, is not safe for `type` or `state_key`: two distinct state keys could collapse into one `room_current_state` primary key.

Required in the delta:
- Enumerate every PostgreSQL sink that a received or authored PDU's strings reach.
- State the rule for each sink: store as text or bytea, sanitise the projection, or refuse at decode.
- Refusing at decode is acceptable for `type`, `state_key`, `sender`, `room_id` and referenced event IDs. Synapse on PostgreSQL cannot persist these either, so refusing does not change which side of a partition Conduit is on. The refusal must be a deterministic per-PDU drop, never a 500.
- The `transactions` request and result columns and the outbox payload must not reject a spec-valid PDU. The simplest fix is `TEXT` holding canonical JSON.
- Error strings must not echo PDU values.
- Add a scenario: a `/send` transaction whose PDU has `\u0000` in `content` returns 200 and the PDU is persisted and readable. A PDU with `\u0000` in `state_key` is dropped with no result entry, and the other PDUs in the same transaction are processed.

### B2. The `/invite` handling of a content-hash mismatch contradicts itself.

- Design `/invite`, step 6: "Persist the received form. That is the redacted form when the hash did not match ... Return `{"event": original_pdu_with_cosignature}`." Under this reading, a hash mismatch is accepted.
- Delta, "Co-signing preserves the author's PDU": "SHALL verify the inviter's signatures **and content hash** ... A failure SHALL return `400 M_INVALID_PARAM` with nothing persisted." Under this reading, a hash mismatch is refused.

Pick one and make both documents and the test say it. Synapse's `on_invite_request` runs `_check_sigs_and_hash`, which redacts on a mismatch, and then continues. Refusing is also safe here, because an invite to a room Conduit is not in creates no DAG partition. If the redacted path is kept, say which form is returned, original or redacted, and test it.

### B3. `admit_fetched` needs a defined expectation per endpoint; `Expect::OneOf` cannot be applied to `send_join` `state`.

The delta says "its derived ID SHALL equal the requested ID, or be in the referenced set" and applies that to the `send_join` response `state`. Conduit never requests those events by ID, and nothing that Conduit already holds references them. The resident server is asserting the room state. Implemented literally, the rule refuses every remote join. Implemented loosely, it does nothing. The design's backfill and `get_missing_events` rule, "or returned as direct ancestors in the requested range", is equally uncheckable: any event in the response can claim to be in range.

Required: define the expectation for each endpoint in the delta.
- `/event`, auth fetch, and the `invite` response: `Exactly(id)`.
- `state` (v1): `OneOf(state_ids ∪ auth_chain_ids)`, which needs a `state_ids` call first.
- `send_join` `state`: no expected ID. The ID is derived and the signature verified. `auth_chain` must lie inside the closure of the `auth_events` of `state ∪ {join}`.
- `backfill` and `get_missing_events`: admitted in reverse topological order. Each event must be one of the requested IDs, or named in `prev_events` by an event that was already admitted from the same response or is held locally.

Add one scenario for the closure case: a `get_missing_events` response that includes an extra, validly signed event that nothing references is not stored.

### B4. The v11 limits are off by one, and two of them are missing.

- **Depth.** The design and the delta say `depth < 2^53-1`. Synapse rejects `depth > MAX_DEPTH`, where `MAX_DEPTH = CANONICALJSON_MAX_INT = 2^53-1` (`api/constants.py:80`, `federation_base.py:362-369`). It also rejects `depth < 0`. The v11 text says "less than the maximum", then "If the room's depth is at the limit, the depth must be set to the limit", so `2^53-1` is a legal depth. As written, Conduit drops an event that Synapse accepts, which is the partition the A1 disposition argues against. Specify `depth` as an integer in `[0, 2^53-1]` and test both ends.
- **Size.** The 65536-byte limit on the canonical PDU, and the 255-byte limits on `sender`, `room_id`, `state_key` and `type`, are not mentioned. For v11, Synapse treats all five as `unpersistable` (`event_auth.py:451-501`, with `strict_event_byte_limits_room_versions: true` for `V11` in `room_versions.rs:295-299`) and drops the PDU (`federation_event.py:1859-1862`). Before this change, unknown keys were discarded. This change persists them durably, so a missing size bound now means storage amplification. Today the only cap is the 16 MiB body limit (`server.rs:1088`). Add these checks to the decode step that enforces the event format, and add a scenario for each.

## Notes for act (non-blocking, ranked)

1. **Serve `content_mismatch` rows as their redaction instead of returning 404.** In both cases, a lossy remote row and a row redacted on receipt, the ID matches and the signatures cover the redacted bytes. A peer that receives `redact(pdu)` sees a hash mismatch, redacts, and derives the same ID. Rows written after the change that were redacted on receipt are inserted as `verified` and served. Legacy rows of the same kind would get 404. That inconsistency withholds auth-chain members from peers for no gain. At minimum, document why `verified` also covers post-change rows redacted on receipt.
2. **State whether `verify_legacy_event_ids` blocks startup.** If it runs in the background, `get_wire_pdu` returns `None` for all history until it finishes. Federation then 404s the whole DAG during that window.
3. **Make the round trip an identity check at decode.** `canonical(decoded Pdu) == canonical(received object minus unsigned)`, otherwise return `PduDecodeError`. This catches every typed-field normalisation in one place, for example `"state_key": null` being dropped on re-encode, which would change both hashes. Synapse uses `AllowMissing<Box<str>>` for `state_key` and refuses null.
4. **Outbound `invite` response.** Beyond `Exactly(id)`, assert that the invitee's server signature is present and verifies. Consider requiring the inviter's domain to equal the X-Matrix origin on inbound `/invite`, as on `send_join`.
5. **`send_join` error codes.** Synapse returns 403 for a sender that is not from the origin and 400 `M_BAD_JSON` for `state_key != sender`. The delta uses 400 `M_INVALID_PARAM` for both. The spec only says "400 invalid", so this is harmless. Record it as a deliberate choice.
6. **Ordering in `admit_fetched` for redacted-on-receipt results.** If a fetched event's hash mismatches, store the redaction. Its ID still equals the request, so the `Exactly` check passes. Add one assertion for this case.

## Verdict

Send-back. A1's rebuttal is correct and should stand, and A2, A4, A5 and A7 are adopted well. B1 is a correctness defect in the A6 resolution: the wedge it was meant to remove still exists one table earlier, on the hot `/send` path. B2 is a direct contradiction between design and delta. B3 is a SHALL that cannot be implemented for `send_join`. B4 contradicts the disposition's own rule (stay on Synapse's side of drop and accept) at the depth boundary and on size. Each fix is a bounded wording and scenario change. None needs a redesign.
