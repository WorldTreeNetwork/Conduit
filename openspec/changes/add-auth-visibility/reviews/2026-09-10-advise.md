# advise: add-auth-visibility

> **ADVISE:** accept
> **READER:** fable-5.1-arch-review
> **SPAWN:** .spawns/add-auth-visibility-1789083547-98016-ccee0e29

## Blind take (written before opening design.md / tasks.md / the delta)

Sources: proposal Why, living-specs process spec, identikey-capability-v1, identikey-auth-challenge-v1, and the cited code in `rooms.rs`, `auth.rs`, `client/mod.rs`, `federation/server.rs`.

1. **Pin: one membership predicate in `conduit`, not four handler-local lookups.** `get_room_state`, `get_state_event*`, `joined_members`, `get_messages` should all call one `conduit` function taking (user_id, current StateMap) → allow/deny; the handler maps deny to 403 `M_FORBIDDEN`. Sync already does its own membership scan (`sync.rs:393-405`); it should call the same predicate.
2. **Pin: `can_see` is 5% of the work; `UserEventPosition` is the other 95%.** The pure predicate needs membership *at the event*, which needs state-at-event. Today nothing computes that (the backfill TODO at `server.rs:883-887` says so). The design must name where state-at-event comes from, or explicitly label the approximation (current membership + compare event depth/stream position against the user's join event) and its failure mode (`joined` visibility over-shows on rejoin).
3. **Refuse: Biscuits that make logout a no-op.** Opaque tokens revoke through `revoke_token` (`mod.rs:477`). A Biscuit verifies offline, so unless the verifier still consults a server-side row (token id → live/revoked, user, device), logout and device deletion stop working. That is a regression from today. Pin: the DB row stays authoritative for liveness and device binding; the Biscuit is the attenuation carrier. Store a token id or hash in `access_tokens`, never raw Biscuit bytes.
4. **Pin: where per-request facts are injected.** Attenuation is decorative unless each room handler injects `room(<id>)` / `op(<name>)` facts and re-evaluates the Datalog. `AuthedUser` as an extractor can verify signature and identity but cannot authorize a room op it does not know yet. The design must say whether `AuthedUser` carries the verified token for a later `authorize(op, room)` call, or whether authorization stays extractor-only in this change (then attenuation must be declared out of scope for v1).
5. **Pin: two restricted-join paths, one fail-closed.** `check_allow_conditions` (`auth.rs:220`) runs inside event auth (`auth.rs:473`), which also gates *federation* `send_join`. Room versions 8+ authorize restricted joins via `join_authorised_via_users_server` plus that server's signature, not by a membership lookup. Failing closed inside event auth would reject valid inbound restricted joins. The fail-closed must land on the CS `join_room` originator path (this server vouching), while event auth checks `join_authorised_via_users_server`.
6. **Refuse: identity on-ramp that mints a Matrix user without a binding rule.** Auth-challenge gives a Blake3 fingerprint; Matrix needs an `@localpart:server`. The design must fix the mapping (fingerprint → localpart, first-login registration policy, collision with password users) or the on-ramp is an open registration endpoint.
7. **Tradeoff I would accept: Biscuit now vs opaque token plus attenuation later.** Cost: Ed25519 verify plus Datalog per request, and the revocation lookup you pay anyway. Benefit: the in-process client can attenuate without a server call. Worth it only if attenuation is exercised in this change or its named successor; otherwise it is an opaque token with extra steps. Accept if the design points at a real consumer.
8. **Pin: federation backfill shares the position derivation.** `is_event_visible_to_server` needs the origin's membership at event time, the same state-at-event problem as line 2. Minimum for this change: `world_readable` → all; otherwise require the origin to have (or have had) a member in the room. Do not write a second derivation.
9. **Pin: license and vectors before the dependency lands.** auth-challenge-v1 §11 says the crate "currently inherits the recrypt workspace license"; the packet asserts Apache-or-BSD. Verify `identikey-auth`'s Cargo.toml before adding it. capability-v1 §8 says no test vectors exist, so the change must carry its own round-trip test against `biscuit-auth` and `identikey-auth`.
10. **Pin: token shape on the wire stays a Matrix bearer string.** Login response, `Authorization: Bearer`, `/whoami`, `logout_all`, and `access_tokens` semantics unchanged from Element's view. A `biscuit:` prefix is fine; anything Element has to parse is not.

## Comparison against design.md, tasks.md, and the delta

The design answers eight of the ten pins directly. Same three-layer split, same "predicates in `conduit`, not axum ifs", Biscuit as attenuation carrier with a named consumer (`add-in-process-client`), epoch for revocation, wire shape unchanged for Element, AGPL kept out by speaking OIDC. Two pins were verified rather than answered: the identikey-auth crate license is `Apache-2.0 OR BSD-2-Clause-Patent` at the workspace root (auth-challenge-v1 §11 is stale, not the design), and fail-closed restricted joins are behavior-neutral today because a joiner is never already a member of the room they are joining, so `check_allow_conditions` already returns false in production; only the unit test at `auth.rs:1176` is green for the wrong reason.

Steelman on the two I pushed hardest: I wanted the DB row to stay authoritative for logout; the design's per-device epoch is the same thing with a better name, and it makes `logout_all` a single update. I worried per-op facts were decorative; the design defers attenuation to the in-process client and root CS tokens carry no room checks, so extractor-only verification is correct for this change and fails closed for any attenuated token that arrives early.

## Notes for act (ranked)

1. **Unlinked fingerprint must not create an account.** Design says "link at register or a first bind"; the delta only covers the linked case. Pin it: an identikey-auth `Response` whose fingerprint has no MXID SHALL fail login. Linking happens only through the registration endpoint under its existing policy, or through a bind that already requires a valid Biscuit. Otherwise the challenge endpoint is open registration. Add the scenario to the delta before fold.
2. **The epoch check is not written, and the obvious way to write it passes trivially.** If the authority block asserts `epoch(3)` and the verifier injects `epoch(4)`, both facts coexist and no check fails. Either inject under a distinct name and put `check if epoch($e), device_epoch($e)` in the authority block, or read the `epoch` fact out in Rust and compare to the device row. The tasks' epoch-bump test will catch the trivial version; write that test first. Also drop the word "offline" from the design: verification does a per-request device-row lookup for epoch, which is fine and equivalent to today's cost.
3. **Name the `UserEventPosition` derivation.** No state-at-event snapshots exist and none are needed: for user U and event E in room R, the position is the membership of U's latest own `m.room.member` event in R with stream position below E's (none → `NeverMember`; invite → `WasInvited`; join → `WasMember`; if U is currently joined and that latest event is after E → `JoinedAfter`). That needs one storage method, member events for (room, user) ordered by position. Backfill uses the same walk over any member from the origin server. Do not write a second derivation.
4. **`may_read_room` drops world_readable peeking.** Matrix lets non-members read `/messages` and `/state` on world_readable rooms. Requiring membership is a defensible v1 cut, but say so in the delta, or let `may_read_room` pass when history_visibility is world_readable and the requester holds a valid grant.
5. **Keep the other-room lookup out of event auth.** When `conduit-jt5` lands, the spec-correct shape is: event auth (room v8+) checks `join_authorised_via_users_server` has invite power and the event carries that server's signature; the CS `join_room` originator does the other-room membership lookup before authoring the join. `check_allow_conditions` inside event auth is the wrong home for either, and this change should leave a comment saying so where it fails closed.
6. **`AuthedUser` should carry the verified authorizer.** Verify once in the extractor, keep the `Biscuit`/authorizer handle on the struct, so `add-in-process-client` can add `room` and `operation` facts per handler without re-plumbing every signature.
7. **Minter key wording.** "Persist it hashed-at-rest like signing keys" is wrong: a private key cannot be hashed at rest. Store it the same way the Matrix server signing key is stored, and treat rotation as a global epoch bump, as the design already says.
