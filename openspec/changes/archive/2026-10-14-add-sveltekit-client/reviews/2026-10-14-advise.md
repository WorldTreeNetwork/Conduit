## Blind take (written before design.md / tasks.md / spec were opened)

1. Pin where the framework-free core lives: `web/` must not import from `client/`, because `remove-react-client` deletes it. Either the core moves to a shared package or it is copied with its tests.
2. Pin the SSO return leg. `redirectUrl` is the app's own origin. `loginToken` is removed from the URL (replaceState) before render and spent once through `m.login.token`. An expired token (120 s TTL) shows a recovery path.
3. Pin the deploy precondition. The app origin must be on `CONDUIT_SSO_REDIRECT_ALLOWLIST`. The server allowlist is a bare prefix match (`http://localhost` also matches `http://localhost.evil`), so that is a server bead, not this change.
4. Pin the fallback when `/login` does not advertise `m.login.sso` (secret unset, OP down). It shows a named error or the password form, not a dead button.
5. Pin the static shape: `ssr=false`, adapter-static SPA fallback, no `+server`/form actions, homeserver chosen at runtime (`?hs=`, well-known), not only at build time.
6. Pin parity with the React proof: WCAG 2.2 AA, the `__conduitClient` hook gated off in prod, real-server Playwright e2e. Spell out what "green" means for `add-svelte-client-proof`.
7. Pin Bun as reproducible: a pinned version, a committed `bun.lock`, CI installs with `--frozen-lockfile`.
8. Refuse an app server, cookies, or a BFF holding the token. Refuse matrix-js-sdk. Refuse fonts loaded from a third-party CDN; self-host them and check each licence (Tactic Sans may not be OFL).
9. Refuse leaving the SSO leg with no test. `POST /_matrix/client/v1/login/get_token` mints a real `loginToken` without the OP, so e2e can prove the `?loginToken=` completion.
10. Tradeoff: shadcn-svelte brings Tailwind and vendored component code. That is fast, but it adds a second styling system next to the hand-built timeline. Pin one token source (CSS variables) that both consume.

The author's core decisions are right, and I would not reopen them:

- A static `adapter-static` SPA with no BFF. The token stays in the browser and the secret stays on `conduit-server`. Conduit's `CorsLayer` already allows any origin.
- Reuse the framework-free core instead of adopting matrix-js-sdk.
- Run `web/` beside `client/` with the React CI job kept until the proof passes.
- Keep `io.identikey.oidc` JWT login out of the UI.

The send-back is about the contract leaving out the parts of SSO that fail in production. It does not question the direction.

## Findings

### 1. The SSO return leg is not specified (blocking)

`sso.rs` sends the browser to `redirectUrl?loginToken=…`. The token lives 120 s (`LOGIN_TOKEN_TTL`) and buys a full access token. The contract should require all of the following:

- The client removes `loginToken` from the address bar (`history.replaceState`) before it renders or loads anything third-party. Otherwise the token sits in history and can reach a `Referer`.
- The client spends the token once through `m.login.token`.
- An expired or reused token (`M_FORBIDDEN`) lands on the signed-out screen with a message and a retry, not a blank shell.
- **The homeserver survives the round trip.** When `?hs=` pins a server, the browser leaves the app and comes back. The client must either encode `hs` into `redirectUrl` or store it in `sessionStorage` before leaving. If it does neither, the return falls back to `http://localhost:8008` and spends the token against the wrong server. This is easy to get wrong and the current spec does not catch it.

### 2. A homeserver without SSO is not specified (blocking)

`main.rs` turns SSO off whenever `CONDUIT_OIDC_CLIENT_SECRET` is unset or OP discovery fails. That is the default local setup in `CLAUDE.md` and in Playwright's global setup. The contract should say:

- The client reads `GET /_matrix/client/v3/login` and offers Identikey only when `m.login.sso` is listed.
- Whether a person sees the password form. Choose one: always, only when SSO is absent, or never, which leaves it test-only. Today's wording ("so automated tests do not require…") reads as test-only. That would leave a person on a homeserver without SSO with no way to sign in.

### 3. The SSO leg has no automated proof (blocking for the proof gate)

No OP is needed to test it. `POST /_matrix/client/v1/login/get_token` (`session.rs`, password UIA) issues a real token from the same `LoginTokenStore` that `m.login.token` spends. Playwright can register with a password, mint a token, and open `web/?hs=<server>&loginToken=<t>`. Then it asserts three things: the signed-in shell appears, the token is gone from `location`, and a second visit with the same token is refused. Pin that as a scenario here so `add-svelte-client-proof` inherits it.

### 4. The Type requirement has a factual error and is not testable

- design.md says "Tactic Sans **stays** the numeral face". No file in `client/` loads or names Tactic Sans. The shipped client loads Atkinson Hyperlegible Next and Barlow Condensed through `@fontsource` (`client/src/main.tsx`). Tactic Sans is a new face with no stated source or licence. The contract should name where it comes from, confirm the licence allows self-hosted web use, and require all three faces to be self-hosted with no third-party font CDN, the way `@fontsource` works today.
- "Wonk axis off": Bricolage Grotesque as distributed exposes `opsz`, `wdth`, and `wght`. `WONK` is a Fraunces axis. The scenario's own check is "at a normal width", which points at `wdth`. Name the actual setting, for example `font-variation-settings` / `wdth 100`, so the scenario can be tested. If an axis really was meant, cite the font build that has it.

### 5. Product principles are not carried into the new capability

`client/PRODUCT.md` holds the accessibility bar (WCAG 2.2 AA, axe with zero serious violations, focus on route change, aria-live) and the rule that the test hook never ships in production. `matrix-client` is the living spec that outlives `client/`. Add one requirement here, or an explicit proof-change scenario, that keeps both. Otherwise they disappear with `remove-react-client`.

### 6. Deploying needs the allowlist (documentation)

`default_sso_allowlist()` covers loopback (so `bun run dev` on `localhost:5173` works), Element, and `element://`. A static deploy on any other origin gets `403 redirectUrl is not allowed` until that origin is added to `CONDUIT_SSO_REDIRECT_ALLOWLIST`. One sentence in design.md and the client docs is enough.

## Outside this change (for the conductor; not owed here)

- **Server: the SSO redirect allowlist is a raw string-prefix match** (`redirect_allowed` in `conduit-server/src/api/client/sso.rs`). `http://localhost` admits `http://localhost.evil.example/`, `http://127.0.0.1` admits `http://127.0.0.1@evil.example/`, and `https://app.element.io` admits `https://app.element.io.evil.example/`. A crafted `sso/redirect?redirectUrl=…` link therefore sends a victim's `loginToken` to an attacker after a real Identikey login. Compare the parsed scheme, host, and port, and treat the path as a prefix. This should be its own server bead. The new client makes this flow the primary sign-in, which raises the stakes.
- Bun: pin the version (`packageManager` or `.bun-version`) and install with `bun install --frozen-lockfile` in CI, matching the pinned pnpm. The proof says core unit tests "run under Bun". The core suite is Vitest, so say whether that means `bunx vitest` or a port to `bun test`.
- shadcn-svelte: say whether Tailwind is adopted. If it is, generate its theme from the same CSS variables the custom timeline uses, so there is one token source.
