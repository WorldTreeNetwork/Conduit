## Blind take

Written from proposal Why/What and the cited code only, before I opened design.md, specs/, or tasks.md.

1. **Core location.** `web/` must not import `../client/src/core`. `remove-react-client` deletes `client/`, so the contract has to say where the framework-free core lives (moved, shared package, or copied) and which node owns that move.
2. **SSO return.** `redirectUrl` must be a static SPA route. The `loginToken` arrives in the query string (`sso.rs` `append_login_token`), so the client strips it with `history.replaceState` before rendering, exchanges it once through `m.login.token`, and handles a token that is expired (120 s) or already used. Callback failures render homeserver HTML (`html_error`) and never come back to the client. Say that.
3. **Allowlist.** The deployed client origin has to be added to `CONDUIT_SSO_REDIRECT_ALLOWLIST`. `redirect_allowed` matches by `starts_with`, so the default `http://localhost` also allows `http://localhost.evil.tld`. That is a server bug and belongs on a server bead, but this contract depends on it.
4. **Flow gating.** Show Identikey only when `GET /login` lists `m.login.sso` with idp `identikey`. Without `CONDUIT_OIDC_CLIENT_SECRET` the server leaves it out, so the contract must name that state instead of shipping a dead button. Also say whether people see password login or only tests do, and what gates it.
5. **Homeserver at runtime.** A static build has no server to template config. Pin the order (`?hs=`, then a build default, then `.well-known` or same origin). An open `?hs=` together with SSO can be used for phishing, so decide what pinning does.
6. **Static hosting.** Pin `adapter-static` with a fallback page and `ssr = false`. Name the host's deep-link fallback requirement and the origin the client is served from. Refuse `+page.server`, `+server`, and `hooks.server`, enforced by a check rather than by prose.
7. **Test hooks.** Keep the same gating as `testHooksEnabled`. Production bundles never expose the automation global.
8. **Bun scope.** Commit `bun.lock`. Say whether Vitest and Playwright run on Bun or on Node through `bun run`. CI runs two toolchains until removal.
9. **Faces.** I agree with refusing Tactic Sans and self-hosting. Check that Atkinson Hyperlegible Next ships `tnum` and that Bricolage's `wdth` axis reaches 100. If it does not, name a fallback.
10. **Tradeoff.** shadcn-svelte brings Tailwind v4 and bits-ui, which is fine for controls. The ground/ink/brass tokens must have one source, or there will be two color systems. PRODUCT.md's WCAG 2.2 AA and axe bar has to carry into `matrix-client`, and PRODUCT.md's React stack lock has to be amended.

Exit test: passes on its face. The client is static, the protocol is standard Matrix, and an SSO-only account can still sign in from Element through the same IdP. No keys or data are captured.

## Send-back: the return leg can send a token to an attacker's homeserver

The spec pins the homeserver in two places (`sessionStorage` and `?hs=` on `redirectUrl`), but it never says which one wins on return. It also never says that a return this tab did not start must not be spent. The proof scenario makes it worse. It "opens the client with `?hs=` and `loginToken`" in a fresh browser context with no prior state, so the obvious build that passes it trusts `?hs=` from the URL.

Attack against that build, using only code that exists today:

1. The attacker builds `https://<legit-hs>/_matrix/client/v3/login/sso/redirect?redirectUrl=https://<web-origin>/?hs=https://evil.example` and sends the link to the victim. `redirect_allowed` accepts it because the prefix is the client's own allowlisted origin (`sso.rs:redirect_allowed`).
2. The victim signs in at Identikey. If they already have an OP session, this can be a single click. The legit homeserver redirects to `https://<web-origin>/?hs=https://evil.example&loginToken=T` (`sso.rs:append_login_token`). The homeserver shows no "continue to this client?" interstitial.
3. The client strips `T`, which satisfies the spec, and spends it against `?hs=`, which is `evil.example`. That server logs `T`, replays it as `m.login.token` at the legit homeserver within 120 s, and gets the victim's access token.

The rule "Never spent against a different homeserver" does not stop this. In step 3, `?hs=` is the pinned homeserver as far as the URL is concerned.

The fix is small and only touches the client contract:

- Before redirecting, the tab writes a pending-SSO record (homeserver plus a nonce, or simply the homeserver) to `sessionStorage`. On return, the client spends `loginToken` only when that record exists and its homeserver equals the return's `hs`. In every other case (no record, a mismatch, or a token with no `hs`) it strips the token, spends nothing, sends no request anywhere, and shows the signed-out screen. `sessionStorage` is per tab and survives the same-tab trip through the OP, so the real flow still works.
- The proof scenario seeds that pending record before it opens `?hs=…&loginToken=…`, for example with Playwright `addInitScript`. A second scenario opens the same URL without the record and asserts that no `/login` request is sent and the signed-out screen shows.

Defence in depth on the server side, which is a server bead and outside this change: show a Synapse-style "Continue to <client>" confirmation before the 302 to `redirectUrl`, or bind the login token to the session that started the redirect. I am recommending it, not requiring it here.

## Notes (not blocking)

- Callback failures (`identikey_callback` → `html_error`) leave the person on a bare homeserver page with no link back to the client. Worth a server bead. The client contract can stay silent about it.
- "SHALL NOT ship an application server" has no mechanical guard. `add-sveltekit-shell` should add a check: no `+page.server.*`, `+server.*`, or `hooks.server.*` under `web/src`, and `adapter-static` in `svelte.config`. That is cheaper than finding out in review.
- `client/PRODUCT.md` still says "React 18 + Vite … not to be relitigated" and will be deleted with `client/`. `add-sveltekit-shell` (or this fold) should write `web/PRODUCT.md`, or point the product record at `matrix-client`, so the next unattended lane does not read the stale lock.
- `add-svelte-session/tasks.md:5` and `add-svelte-client-proof/tasks.md:4` restate the return leg. Once this spec is amended they should pick up the pending-record condition. Those paths are outside my write scope.
- Static hosts need a deep-link fallback (`200.html` / `index.html`) for the SSO return route. That is a shell or deploy detail, and it follows from "SPA fallback".
