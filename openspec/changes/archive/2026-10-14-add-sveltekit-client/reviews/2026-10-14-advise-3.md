## Blind take (written before opening design.md or tasks.md)

Sources: proposal.md Why/What, `conduit-server/src/api/client/sso.rs`, `client/src/config.ts`, `client/PRODUCT.md`. No living `matrix-client` spec exists.

1. Pin: `loginToken` is spent only if a pending-SSO record written before the redirect matches the return (hs at least); otherwise drop it. The server binds nothing to the client, so without this any link `web/?loginToken=<attacker's>` logs the victim into the attacker's account (login CSRF).
2. Pin: strip `loginToken` from the URL (`history.replaceState`) before any network call or render that could leak it, and spend it exactly once (it is one-shot, 120 s TTL).
3. Pin: the redirectUrl the client sends must be on `CONDUIT_SSO` allowlist; the server check is a raw `starts_with` (`sso.rs:391`), so `http://localhost` also admits `http://localhost.evil.example`. The client cannot fix that, but the contract should name the deployed origin entry and not rely on the default list.
4. Pin: the token is POSTed only to the hs recorded in the pending record, never to a `?hs=` read off the return URL.
5. Pin: sign-in choices come from what `GET /login` advertises (`m.login.sso` + `identity_providers`, `m.login.password`), so a homeserver without OIDC is not a dead screen. "Password stays for automated tests" must say whether humans see it.
6. Pin: homeserver resolution order for a static app. `config.ts` comment promises "the page's own origin when served by a homeserver" but the code falls to localhost.
7. Pin: where `client/src/core` lives once `remove-react-client` deletes `client/`; web/ must not import across into a directory scheduled for deletion.
8. Pin: access/refresh token storage and that production bundles never expose test hooks (parity with `testHooksEnabled`).
9. Refuse: any server-side piece (adapter-node, SSR, a callback route on a client server). Static fallback hosting only.
10. Tradeoff: a sessionStorage record is per-tab, so an Identikey flow that finishes in another tab/device returns with no record and fails closed. That is the right default (fail closed beats login CSRF), but it must be stated and give a recovery action.

Steelman of the authors' position: the advise-2 attack (an unsolicited return carrying `?hs=evil`) needs the victim's tab to hold a record that names `evil`. A fresh link has no record, so the token is stripped and nothing is sent. The proof leg seeds the record (`add-svelte-client-proof/tasks.md:4`), and a second case asserts that no `/login` request goes out without it, so the build that trusts `?hs=` alone now fails a test. `add-svelte-session/tasks.md:5` carries the same condition. `POST /_matrix/client/v1/login/get_token` exists (`session.rs:250`), so the proof needs no hosted OP. The send-back is closed.

## Residual risk: relayed SSO (not blocking, server-side)

The pending record stops returns this tab did not start. It cannot stop a homeserver the person chose from relaying SSO. If a victim opens `web/?hs=https://evil.example` and presses Identikey, the tab records `evil`. `evil` can then 302 to `https://<legit-hs>/_matrix/client/v3/login/sso/redirect?redirectUrl=https://<web-origin>/?hs=https://evil.example` (allowlisted, `sso.rs:391`). The victim signs in at Identikey. The legit homeserver returns `?hs=evil&loginToken=T`, the record matches, and the client spends `T` at `evil`, which replays it at the legit homeserver within 120 s.

The client cannot close this on its own: the record and the return agree because the victim really did start at `evil`. The real fix is on the server, which this proposal puts out of scope: a Synapse-style "Continue to <client> as <mxid>?" confirmation before the 302 in `identikey_callback`, or a login token bound to the browser session that started the redirect. Advise-2 already recommended this as defence in depth. No bead exists for it (only `conduit-sw8` and `conduit-y99.18.2`). **The conductor should file one.** My write scope does not include beads.

There is also a cheap client-side partial fix for `add-sveltekit-shell` / `add-svelte-session`: whenever Identikey is offered, the signed-out screen names the homeserver host, even when `?hs=` pins it and hides the field (the React client hides it, `client/src/config.ts:20`).

## Notes for the build nodes (not blocking)

- **Record lifecycle.** The spec says when the record is required, but not when it ends. `add-svelte-session` should clear it on every return (spent, refused, or stripped) and give it an expiry around the server's `SESSION_TTL` (600 s, `sso.rs:36`). If it does not, a tab that once signed in will keep accepting a later `?hs=<same>&loginToken=<attacker's>` and becomes a login-CSRF window. Playwright `addInitScript` re-seeds on every navigation, so the proof will not catch a missing clear. Add a unit test.
- **Comparison.** Compare normalized origins, not raw strings, so a trailing slash or a case difference does not make a real sign-in fail.
- **"Before render" in SvelteKit.** The router owns history. Strip the token in an inline script in `app.html` before hydration, or in the root `+layout.ts` before any `page.url` reader runs. Keep both the token and the `hs` it came with in memory.
- **Return while signed in.** If a `loginToken` arrives while a session already exists, the spec does not say what happens. Simplest rule: strip it, do not spend it, keep the existing session.
- **hs resolution order** (take 6). `config.ts`'s comment promises a same-origin fallback that the code does not implement. `add-sveltekit-shell` should pin `?hs=` → build default → `.well-known` or same origin, and choose what a bare origin falls back to.
- **CSP.** The token sits in `localStorage` and the app is static. A `<meta http-equiv="Content-Security-Policy">` with `connect-src` limited to the homeserver is not possible with a free `?hs=`, but `script-src 'self'` is. Worth a shell task.
- Advise-2 notes still open: no mechanical guard against `+server`/`+page.server`/`hooks.server`, and `client/PRODUCT.md`'s stale React lock. Neither belongs to this contract.

## Exit test

Passes. The client is static and speaks standard Matrix. An SSO-only account can sign in from any Matrix client through the same IdP. Keys and data stay with the homeserver the person chose.
